# はじめに

[前回のベンチマーク](./mastra-mcp-benchmark.md)では、7 モデルを MCP なし / mastra-mcp / Context7 で比べ、強いモデルでは MCP の効果が小さいことが分かりました。第 3 ラウンドでドキュメント固有の挙動を要求しても、「MCP なしだと失敗する、または高くつく」ケースはほとんど作れませんでした。

今回は、モデルが学習していなさそうな **新しい API** に絞って確かめます。弱めのモデルで、条件を MCP なしと mastra-mcp に絞り、各セルを 3 回繰り返してばらつきも見ます。さらに同じ実験をもう一度実行して、結果が再現するかも確かめます。

# 条件

| 項目 | 内容 |
|---|---|
| モデル | claude-haiku-5.5、gpt-5.6-luna、gpt-5.6-terra、gpt-5.3-codex |
| 条件 | MCP なし / mastra-mcp(Context7 は今回なし) |
| アプリ | d1〜d5(下記)、隠しテスト合計 24 |
| 繰り返し | 各セル 3 回(合計 120 回)を 2 回実施(合計 240 回) |
| 実行環境 | GitHub Copilot CLI、`@mastra/core` 1.76、Web 取得は無効、`@mastra/*/dist/docs` は削除 |
| LLM | アプリのテストは `ai/test` のモックモデル。外部ネットワークと API キーは使わない |
| 並列度 | 12 並列。時間は参考値 |

`dist/docs`(インストール済みパッケージ同梱ドキュメント)は削除しましたが、`node_modules` の型定義(`.d.ts`)と実装コードは、モデルがそのまま読めます。この点は結果の解釈に効きます。

## 5 つのアプリ

いずれも、Mastra の比較的新しい機能です。「Added in」は公式ドキュメントの記載です。

| ID | 機能(Added in) | 要求した内容 | ドキュメント固有の点 |
|---|---|---|---|
| d1 | スケジュールワークフロー | 宣言的 `schedule` と `mastra.schedules`(create / update / pause / resume / run / delete) | `startWorkers()` が必要、ID 規則(`wf_<id>` / `wf_<id>__<scheduleId>` / `schedule_<slug>`)、pause は永続、`run()` の `claimId` が `runId` |
| d2 | バックグラウンドタスク(1.29) | ツール単位・エージェント単位の `background`、`untilIdle`、`_background` 上書き、suspend / resume | 対象外ツールは上書きされても前景実行、`_background` は実行前に除去、`untilIdle` なしではストリームが先に閉じる |
| d3 | ゴール(1.43) | `goal`、`setObjective`、`maxRuns`、`goal` チャンク | 予算切れで `paused`、judge が有効化スイッチ、一時停止は `updateObjectiveOptions`、judge は JSON `{decision, reason}` を返す |
| d4 | durable agent(1.45) | `createDurableAgent`、`observe(runId)`、`cleanup`、承認 | `stream()` は `{output, runId, cleanup}`、切断後も `observe` で全チャンクを再生、承認は `resume(runId, {approved})` |
| d5 | シグナル(1.39) | `sendMessage` / `queueMessage` / `sendNotificationSignal` / `sendStateSignal` | 待機中は `wake`、実行中は同じ run に `deliver`、`queueMessage` は次の run、通知の `dedupeKey` で集約、状態シグナルは thread が必要 |

参照実装は私が作り、仕様テストを 3 回連続で通して確認しました。タスク文は、ドキュメント由来でない部分(エクスポート名、戻り値の形、モックの動作)を具体的に書き、ドキュメント固有の挙動は「振る舞い」として要求しています。

# 結果(1 回目の実験)

## 条件別の合計(4 モデル × 5 アプリ × 3 回)

| 条件 | 合格テスト | 全テスト合格の回数 | クレジット | 所要時間(合計) |
|---|---|---|---|---|
| MCP なし | 286/288 | 58/60 | 2,186.0 | 2:53 |
| mastra-mcp | 279/288 | 55/60 | 1,942.6 | 2:46 |

- **成功率は MCP なしの方が高い**結果でした(全合格 58 対 55)。
- **クレジットは mastra-mcp の方が約 11% 少ない**です(2,186 対 1,943)。時間もわずかに短いです。
- mastra-mcp 条件で、1 回あたりの MCP 呼び出しは平均 2.7 回でした。

## 失敗の内訳と、d3 の採点訂正

最初の採点では d3 の失敗が 10 回(mastra-mcp 7、MCP なし 3)あり、「mastra-mcp で d3 が悪化した」ように見えました。原因を調べると、**私のタスク文の曖昧さ**でした。

- `runGoal` の戻り値について「text は最終テキスト」と書きました。参照実装は `await out.text`(最後のイテレーションの text、`'work 2'`)を返します。
- 10 回のモデルは、すべて `fullStream` の `text-delta` を全イテレーション分連結していました(`'work 1work 2'`)。10 回とも、同じ 1 テストの同じ assertion で落ちています。
- MCP なしの luna も 3 回とも同じ理由で落ちたため、MCP の有無とは無関係です。

そこで仕様を「text が最終テキストで終わる」に緩め、d3 の 24 回を再採点しました。**d3 は両条件とも 12/12 全合格**になりました(上の表は再採点後の値です)。c2・c4(第 3 ラウンド)と同様、実行後の仕様変更なので、この点は限界にも書きます。

再採点後の失敗は 7 回です。

- **d4(durable agent)**: 3 回、いずれも mastra-mcp(haiku 2 回、terra 1 回)。haiku の 1 回は 5 テストすべてが落ちた(ほぼ動かない実装)ケースです。terra の 1 回は承認の `resume` で落ちました。
- **d1(スケジュール)**: 3 回(luna の MCP なし 2 回、mastra-mcp 1 回)。MCP なしの 2 回は `mastra.schedules.create` の正規化 ID のテストです。
- **d5(シグナル)**: 1 回(terra、mastra-mcp)。

# 再実験(同じ条件でさらに 3 回)

結果が再現するかを確かめるため、同じ 120 回(4 モデル × 2 条件 × 5 アプリ × 3 回)をもう一度実行しました。d3 は修正後の仕様で採点しています。以降、最初の 3 回を「1 回目の実験」、追加の 3 回を「再実験」と呼びます。

## 再実験での失敗

再実験の失敗は 11 回でした。

- **d1(5 回)**: luna が 3 回(MCP なし 1、mastra-mcp 2)、terra と codex が各 1 回(いずれも MCP なし)。1 回目の失敗と同じく、`mastra.schedules.create` の ID などが中心です。luna は両条件とも落ちました。
- **d4(4 回)**: haiku が両条件で各 1 回、codex が MCP なしで 2 回(1 回目の実験では codex の MCP なしは d4 を全合格していました)。
- **d5(2 回)**: terra の MCP なし。1 回目の d5 の失敗は terra の mastra-mcp でした。

どの失敗も、モデルやアプリごとに偏っています(d1 の luna、d4 の haiku と codex)。MCP の有無よりも、アプリとモデルの組み合わせによる難しさの方が、失敗を左右しているように見えます。

# 考察

## 新 API でも、MCP なしで通る

「新しい API なら MCP なしで失敗しやすいはず」という仮説は、今回の結果では支持されませんでした。MCP なしは 6 回分の合算で 120 回中 110 回が全合格です(mastra-mcp は 112 回)。

理由として考えられるのは次の 2 点です。

1. モデルが見ているのは `node_modules` の型定義と実装コードです。`dist/docs` を消しても、`.d.ts` や `dist` の JS が残っているため、新 API でも調べられます。
2. 今回の各アプリは、仕様テストが検証する挙動を、タスク文が相当の部分まで書いています。ドキュメントを読まないと分からない部分は、前回より少なかった可能性があります。

## MCP の効果は、成功率ではなくコストと時間に小さく出た

- **成功率**: 差はありません。1 回目と再実験で向きが入れ替わり、合算は 112 対 110 でした。
- **クレジット**: 合算で約 5.5% 少なくなりました。ただし 1 回目は約 11% 少なく、再実験はほぼ同じでした。安定して出たのは d2(約 29% 減)だけです。
- **時間**: 4 モデルとも mastra-mcp が短い傾向でした。差は小さいです。
- d2 で下がった理由は、MCP なしのモデルが `node_modules` を広く読み込んで探索していたのに対し、mastra-mcp が該当ページを直接示せたためと考えていますが、探索内容は確認していません。

## 1 回目の実験の読み違い

1 回目の実験だけを見ると、「MCP なしの成功率が高い」「d3・d4 で mastra-mcp が悪化」と読めました。再実験でその傾向は逆転し、d3 は別の原因(タスク文の曖昧さ)でした。**3 回の繰り返しでも、成功率の差は読み取れない**ことが分かりました。

# 結論

- 今回の条件では、「新 API だから MCP が必要」とまでは言えませんでした。弱めのモデルでも、型定義と実装コードが読めれば MCP なしで通ることが多いです。
- mastra-mcp は、成功率を変えず、クレジットと時間を小さく減らす傾向でした(合算で約 5.5% 減)。d2 のように広く探索させるアプリでは、約 29% 減でした。
- コストと品質を両立するには、軽量モデル(haiku-5.5)を使うのが、今回の実測では最良でした(合算 143/144、103 クレジット。terra の約 1/14、codex の約 1/24)。mastra-mcp は、そこに足して少し下げる程度です。

使い分けとしては、次のようになります。

- 型定義と実装コードが読める環境では、MCP なしを基本にします。
- コストと時間を少し下げたい場合や、広い API を探索させる場合は、mastra-mcp を足す価値があります。
- 成功率を上げる目的で足すのは、今回のデータでは根拠がありません。

# 注意点と限界

- 各セル 6 回、合計 240 回の実行です。それでも成功率の差(110 対 112)は偶然の範囲で、有意とは言えません。
- 仕様テストは私が作りました。d3 は、1 回目の実験後にタスク文の曖昧さ(`runGoal` の `text`)に気づき、仕様を「最終テキストで終わる」に緩めて再採点しました。再実験の d3 は最初から修正後の仕様です。他のアプリにも同様のずれが残っている可能性があります。
- Context7 は今回の比較に含めていません。
- 12 並列で動かしたため、所要時間は参考値です。
- 失敗の原因分析は、d3 の全 10 件と、d1・d4 の一部を再実行して確認した範囲です。他の失敗は原因を確定していません。
- `dist/docs` を削除しているため、本番での「インストール済みドキュメントを使う」運用とは条件が異なります。

```bash
# 実行(例): モデル、条件(none | mastra)、アプリ(d1〜d5)、繰り返し番号
```
